## Goals / Non-Goals

**Goals:**
- Any post can embed a single image with plain markdown `![alt](./photo.jpg)` syntax (image colocated in the post's own content folder) and get responsive/optimized output automatically.
- Posts with multiple related images can present them as a grid via a `Gallery` component, without per-post custom layout code, and without needing per-image `astro:assets` resolution logic duplicated in React.
- Clicking or keyboard-activating any embedded image (standalone or within a `Gallery`) opens a full-size lightbox view; inside a `Gallery`, the lightbox supports next/previous navigation between that gallery's images.
- Lightbox is keyboard-accessible (operable to open, not just to close/navigate once open) and screen-reader-accessible (focus trapped inside while open, accessible name for the dialog).

**Non-Goals:**
- A `heroImage`/`cover` frontmatter field or any post-listing-page image treatment — this covers in-body content images only.
- Remote/external image URLs — `astro:assets`' remote-image path exists (confirmed in `rehype-images-to-component.js`'s `isRemoteImage` branch) but this design scopes to locally colocated images only, matching the "no existing convention" starting point; remote images can be a follow-up if a post ever needs one.
- A remark-shortcode-to-JSX-component transform for galleries (e.g. detecting "adjacent markdown images" and auto-wrapping them). See Decisions below for why `Gallery` is a hand-authored wrapper instead.
- Guaranteeing the lightbox always serves a strictly higher-resolution image than the grid thumbnail — see Risks: this design reuses the same optimized `<img>`/`srcset` the grid already rendered rather than requesting a separate larger derivative, accepted as good-enough for a personal blog's scale (see Risks for the reasoning and revisit trigger).
- Image editing/cropping/upload tooling — this is a static-site blog; images are added to the repo like any other content file.
- Fixing the pre-existing broken `/favicon.svg` reference in `Layout.astro:44` — unrelated dead reference found during the audit, out of scope for this change (flagged separately).
- New automated tests for `Gallery.tsx`/`Lightbox.tsx` — `vitest.config.ts`'s `test.include` is `['src/**/*.test.ts']` only (confirmed by reading the file), which would silently skip any `.test.tsx` file using JSX-based rendering (e.g. React Testing Library). Widening that glob to include `.test.tsx` and deciding on a component-testing approach is real scope, not a rubber-stamp addition — treated as a separate follow-up rather than folded into this change (see Open Questions).

## Decisions

### Asset pipeline: rely on `@astrojs/mdx`'s existing automatic `astro:assets` rewrite, plus one global `astro.config.mjs` `image` config for responsive `srcset` — no explicit `<Image />` authoring required for the single-image case

Confirmed via `node_modules/@astrojs/mdx/dist/rehype-images-to-component.js`: every `.mdx` file in this repo already gets local-relative `<img src="./x.jpg">` output (which is what markdown `![]()` compiles to) rewritten into an auto-imported `astro:assets` `<Image>` component. This is existing behavior of the already-installed `@astrojs/mdx@7.0.3` — nothing to configure for the rewrite itself (see Context's deprecation caveat for the adjacent, unrelated plugin-wiring deprecation).

**Correction from empirical verification (task 1.1, 2026-08-07)**: an earlier draft of this design claimed the automatic rewrite alone produces a responsive `srcset` with zero configuration. That's wrong — verified false by adding a real image to a scratch post and inspecting the rendered `<img>` via the running dev server: with this repo's `astro.config.mjs` as it stood before this change (no `image` key at all), the output had a single `f=webp` format-converted candidate and **no `srcset` attribute**. Reading `node_modules/astro/components/Image.astro` explains why: `const layout = props.layout ?? imageConfig.layout ?? 'none'`, and `getImage()` only emits multiple `srcSet` candidates when `layout` isn't `'none'`. `rehypeImageToComponent` (the automatic rewrite) only forwards `widths`/`densities` props if they're already attributes on the parsed `<img>` node — and plain markdown `![]()` syntax never produces those. So the rewrite alone gives format optimization only, never a responsive `srcset`, regardless of markdown authoring.

**Fix, verified empirically**: setting `image: { layout: 'constrained', responsiveStyles: true }` in `astro.config.mjs` (both default to `'none'`/`false` when the `image` key is absent, confirmed by reading `node_modules/astro/dist/core/config/schemas/base.js`) makes `getImage()` emit a full breakpoint `srcset` on every automatically-rewritten image, no per-image props needed. Verified via the dev server against the scratch post's 2400×1600 test image: `srcset` candidates were `640w, 750w, 828w, 1080w, 1280w, 1668w, 2048w, 2400w` (Astro's default breakpoint list, capped at the source's natural width) plus an auto-generated `sizes="(min-width: 2400px) 2400px, 100vw"`. `responsiveStyles: true` is required separately — without it, `layout: 'constrained'` still emits `data-astro-image-fit`/`data-astro-image-pos` attributes but no accompanying CSS to interpret them (that flag defaults to `false`; without it those attributes are inert). Confirmed both flags together render correctly (proper aspect ratio, no distortion, no letterboxing) via Playwright screenshot in light and dark mode against the scratch post. This is a global config change — it affects the render behavior of every `astro:assets` image in the site, not just this feature's, though since image embedding is greenfield (Context) nothing existing is affected today.

**What this means for authoring:** a post author writes `![A red bicycle leaning against a brick wall](./bicycle.jpg)` with `bicycle.jpg` colocated in the post's `YYYY-MM-DD_slug/` folder, and gets Astro's full optimization pipeline (responsive `srcset`, format negotiation) automatically, once the `astro.config.mjs` `image` config above is in place. This satisfies the epic's "plain markdown image syntax at minimum" goal exactly, with zero new code for the single-image case beyond that one-time global config.

**Alternative considered and rejected**: requiring authors to explicitly `import myImage from './photo.jpg'` and use `<Image src={myImage} alt="..." />` JSX (the pattern Astro's own docs lead with for `.astro` files, and the pattern `astro:assets`' `Image` component and `getImage()` function are actually designed for — both are Astro-runtime constructs: `Image` is an `.astro` component (`node_modules/astro/components/Image.astro`), not a React component, and `getImage()` returns a `Promise`, incompatible with this repo's synchronous, `react-dom/server`-based `@astrojs/react@6.0.1` rendering — confirmed by inspecting both during independent review). Rejected for the single-image case because it's strictly more authoring friction than plain markdown syntax for no benefit — the automatic rewrite already produces the same underlying `<Image>` component server-side. This confirmed incompatibility is also why `Gallery` (below) cannot call `getImage()`/`<Image>` directly from React, which an earlier draft of this design incorrectly proposed as a fallback.

### Gallery: hand-authored `<Gallery>` wrapper around plain-markdown image children, not a structured `images` prop and not a remark-shortcode transform

The repo has two authoring patterns in active use, per the epic's own framing (`abf-k7d.2`'s description) and this session's audit of `src/components/`:
1. **Remark-shortcode-to-JSX** (callouts, math, mermaid — see `content-polish-widgets` spec): markdown-native syntax detected by a remark plugin, rewritten into a component reference. Fits when there's a natural markdown syntax for the concept and the transform is unambiguous.
2. **Hand-authored JSX-in-MDX with structured props** (`EChart.astro`/`EChart.tsx`, `PigeonMap.tsx` — confirmed present in `src/components/`, one level above `src/components/ui/`): the author writes a component tag directly in MDX with explicit props, for widgets whose input is structured data, not prose-adjacent markdown syntax.

A gallery's *grouping* (which images belong together, and in what order) is structured — there's no markdown syntax for "these N images are one gallery" — but each individual *image* already has a perfectly good, already-optimized markdown syntax (`![]()`). Forcing images into a JS prop as raw string paths (`images={[{src: './a.jpg', alt: '...'}]}`) would have required `Gallery.tsx` to resolve those paths to optimized assets itself — which, per the Asset pipeline decision above, isn't achievable from a React component (`Image`/`getImage()` are Astro-runtime-only). An earlier draft of this design proposed exactly that structured-prop shape with a "fall back to `getImage()`" escape hatch; independent review caught that the escape hatch doesn't actually work, forcing this revision.

**Revised decision**: `Gallery` takes its images as MDX **children**, each written with plain markdown syntax, e.g.:
```mdx
<Gallery>

![A red bicycle](./a.jpg)

![A blue bicycle](./b.jpg)

</Gallery>
```
**Authoring requirement, verified empirically (task 4.1, 2026-08-07)**: each image needs a blank line before and after it, as shown above. Without blank lines separating them, standard CommonMark treats consecutive non-blank lines as one paragraph — all the images end up as sibling `<img>` nodes inside a *single* `<p>`, which collapses `Gallery`'s CSS grid to one column (the lone `<p>` is the only grid item; the images then just stack inside it). Confirmed by rendering both forms against the scratch post: no blank lines produced one `<p>` wrapping all 3 images and a broken single-column layout; blank lines between each produced 3 separate `<p>` elements and the correct 3-column grid. This is a CommonMark authoring detail, not a `Gallery.tsx` bug — worth flagging explicitly since this document's own earlier draft of this example (and the epic's blog-authoring conventions generally) didn't call it out, and it's easy to get wrong by analogy with how adjacent JSX tags don't need blank lines between them.

Markdown syntax nested inside JSX flow-element children in MDX is still parsed as markdown by the same compiler pass — `rehypeImageToComponent`'s `visit(tree, "element", ...)` walks the whole rehype tree, not just top-level nodes, so each nested `![]()` still gets rewritten into an `<Image>` and rendered to optimized static HTML server-side, *before* it's ever passed to `Gallery.tsx` as `children`. `Gallery.tsx` (the React island) receives already-rendered, already-optimized `<img>` markup as opaque slot content — confirmed by reading `node_modules/@astrojs/react/dist/vnode-children.js`: `@astrojs/react` has a dedicated mechanism (`convert()`) that parses pre-rendered HTML string children via `ultrahtml` into real React vnodes before handing them to the island as `props.children`, specifically so a framework island can receive Astro-rendered static content across the hydration boundary — and only needs to lay that content out in a grid and hand it to `Lightbox` as a navigable set. `Gallery.tsx` never touches image resolution, so the earlier "does the rewrite still fire for prop-passed paths" question doesn't arise: there's no prop-passed path to resolve.

**Alternative considered and rejected (structured `images` prop)**: rejected per above — not implementable without a working Astro-runtime-to-React image-resolution bridge, which doesn't exist for this repo's synchronous React rendering setup.

**Alternative considered and rejected (remark plugin auto-detecting adjacent images)**: rejected — no natural syntax boundary exists, and implicit grouping-by-adjacency is fragile (what stops the count if a caption or blank line intervenes? does a single stray image between two galleries silently merge them?). Explicit `<Gallery>...</Gallery>` wrapping avoids all of this ambiguity while still letting each image use its familiar, already-optimized markdown syntax — arguably better authoring ergonomics than the rejected structured-prop shape, since there's no relative-path string to hand-type or typo.

### Single-image lightbox wiring: client-side DOM enhancement, not an MDX `components={{ img: ... }}` override

**Correction from empirical verification (task 3.1, 2026-08-07)**: an earlier reading of this design assumed the standalone-image click-target could be wired in automatically by overriding `img` in the shared `components` map passed to `<Content components={{...}} />` (`src/pages/blog/[...slug].astro:84`, the same mechanism `MDXComponents`/`mdx-components.tsx` already uses for `Callout`/`CodeBlock`). Tested directly: this override **does** intercept the astro:assets-rewritten image (confirmed by rendering a debug component in its place), but it fires *before* `getImage()` resolution — the override receives only the raw pre-optimization props (`{ alt: string, src: ImageMetadata }`, where `src` is `{ src, width, height, format }` pointing at the *original unoptimized* file, not `getImage()`'s output). Since `getImage()`/`astro:assets`' `Image` component are Astro-runtime-only and unusable from a React component (see the Asset pipeline Decision above), any component substituted at this override point would have to reimplement `astro:assets`' resolution from scratch or ship an unoptimized image — a straight regression against task 1.1's fix. Rejected.

**Alternative considered and rejected**: a custom remark plugin (matching the existing `remarkCallout`/`remarkMermaidToComponent` pattern) that wraps `img` mdast nodes in an intermediate wrapper element before `@astrojs/mdx`'s internal `rehypeImageToComponent` runs, relying on its `visit(tree, "element", ...)` walk finding the nested `img` regardless of wrapper depth. Plausible in principle but depends on undocumented internal traversal behavior of a third-party compiler-internal pass (not a public plugin hook) — fragile against a minor-version internal refactor, and unverifiable without forking/patching the dependency to add temporary instrumentation. Rejected in favor of a mechanism that doesn't depend on `@astrojs/mdx` internals at all.

**Decision**: `src/components/PostImageLightbox.tsx`, a single React island (one per post, not one per image) rendered once in `src/pages/blog/[...slug].astro` right after `<Content .../>`. After hydration, it queries its container (`.prose`) for `img[data-image-component="true"]` elements not already inside a `[data-gallery]` container (reserved for `Gallery`, task 4.x, so `Gallery` can own its own click-wiring with cross-image navigation instead of being double-wrapped), and for each one performs a direct DOM operation: create a real `<button type="button">`, `img.replaceWith(button)`, `button.appendChild(img)`. Click/keyboard activation on the button opens a single shared `Lightbox` instance with a one-element image set built from the *already-rendered* `img.src`/`img.alt` (the real DOM values after the browser's own srcset negotiation, not a prop re-derivation). This satisfies every constraint simultaneously: zero per-post JSX authoring (fully automatic, matching the epic's "at minimum" goal), the SSR output is completely untouched by this mechanism (astro:assets optimization from task 1.1 is preserved byte-for-byte), and post-hydration the click target is a genuine native `<button>` element (focusable, Enter/Space-activatable, no synthetic `tabindex`/keydown handling needed) rather than a click handler on a bare `<img>`.

**Verified** (Playwright, JS-disabled context + JS-enabled context against the scratch post): with JavaScript disabled, the image renders normally inline and zero buttons are injected (clean progressive-enhancement fallback). With JavaScript enabled, exactly one `<button data-lightbox-trigger>` wraps the image, the original `<img>` (with its full `srcset`) is preserved unmodified inside it, and both mouse click and keyboard (Tab to focus, Enter) activation open `Lightbox` correctly.

**Second correction, hydration directive (task 3.2, 2026-08-07)**: this design's Decisions section (Lightbox, below) states `client:visible` for `Lightbox`-adjacent islands, citing `TableOfContents.tsx`'s precedent. Tested directly against `PostImageLightbox`: **`client:visible` never hydrates it.** `PostImageLightbox` renders `<Lightbox images={[]} .../>`, and `Lightbox` returns `null` when there's no current image (its initial/idle state) — so the astro-island wrapper for `PostImageLightbox` resolves to a zero-footprint element. Astro's `client:visible` hydrates via an `IntersectionObserver` on the island element itself; a zero-size element has no meaningful intersection ratio and the observer callback never fires (confirmed: added temporary `console.log` inside the effect — with `client:visible` it never printed even after a 2s wait with the page fully loaded; switching to `client:idle` made it print immediately). `TableOfContents.tsx`'s `client:visible` precedent doesn't hit this because that component always renders a real, visibly-sized nav sidebar — it has no all-null initial-render state. **Decision**: `PostImageLightbox` uses `client:idle` instead — it doesn't depend on the island having any visible footprint, and its whole job (attaching handlers to already-visible content elsewhere on the page) has no inherent "wait until visible" semantics to begin with, unlike `TableOfContents`' own scroll-spy which genuinely needs viewport-intersection data. `Lightbox` itself (when rendered directly with a non-empty image set, e.g. by `Gallery` in task 4.x) is a different case and may still use `client:visible` correctly if its own wrapper has real content — revisit per-component, not as a blanket rule.

### Image-to-lightbox click target: a focusable, keyboard-operable wrapper, not a bare click handler on `<img>`

Independent review caught that a plain `<img>` element is not focusable or keyboard-operable — a `click` handler alone gives mouse/touch users a way to open the lightbox but leaves keyboard users with no way to trigger it at all, contradicting this design's own accessibility goal (which, in an earlier draft, only covered keyboard behavior *after* the lightbox was already open). **Decision**: wrap each lightbox-eligible rendered image in a `<button type="button">` (native focusable, `Enter`/`Space`-activatable, no `tabindex`/keydown-handling boilerplate needed) rather than attaching a click handler directly to the `<img>`. This applies uniformly to both the standalone single-image case and each image inside `Gallery`.

### Lightbox: `@headlessui/react`'s `Dialog`, not raw native `<dialog>`

Both viable native mechanisms found in `modern-web-guidance` (`<dialog closedby="any">` and Invoker Commands) are Newly Available, not Baseline Widely Available, and each needs a distinct manual-fallback or polyfill to reach this repo's implicit "just works" bar (no stated browser-support policy in `AGENTS.md`, so treating "Newly Available without fallback" as too narrow). `@headlessui/react`'s `Dialog` provides focus-trap, portal rendering, `aria-*` wiring, and Esc/backdrop-click dismiss out of the box, is already a project dependency, and is already the established pattern here for other interactive primitives (`Button`, `DataInteractive`) — using it for a third primitive is more consistent with existing conventions than introducing either native-`<dialog>`-plus-polyfill path for a repo that hasn't needed one yet.

**Alternative considered and rejected**: native `<dialog closedby="any">` with the guide's documented Safari fallback script. Rejected primarily on consistency grounds (this repo has zero raw native-`<dialog>` usage today and one existing headlessui-Dialog-adjacent gap to fill) plus avoiding hand-writing and testing a click-coordinate-bounds fallback script that `@headlessui/react` already solves. Revisit if `@headlessui/react` is ever dropped as a dependency for unrelated reasons.

**Lightbox component shape**: `src/components/Lightbox.tsx`, a client-side React component wrapping `@headlessui/react`'s `Dialog`. It needs open/close state and (for gallery navigation) "current index" state — client-side interactivity, so per `AGENTS.md`'s Astro-glue/React-logic split this is a React component, hydrated with `client:visible` (consistent with `abf-k7d.1`'s `TableOfContents.tsx` precedent — content images and galleries are typically already in or near the viewport by the time a reader could click one, so eager `client:load` hydration isn't needed). `Lightbox` receives "the full navigable image set" (an array of already-rendered `<img>` sources/alt text, plus the clicked index) as a prop at open time from whichever wrapper opened it (the standalone single-image wrapper passes a one-element set; `Gallery` passes its full children set) rather than inferring gallery membership from DOM structure at click time.

**Lightbox image resolution**: `Lightbox` reuses the same already-rendered, already-optimized `<img>`/`srcset` from the grid/inline context rather than requesting a separate larger derivative — see Risks for why this may show a lower-resolution image than ideal when displayed at full-viewport size, and the accepted trade-off.

**Image loading priority** (per `optimize-image-priority`): omit `fetchpriority` on ordinary in-body post images (default priority, not LCP candidates in the typical case — a post's lead content is usually text, not an image) and add `loading="lazy"` for images likely to be below-the-fold, i.e. any image inside a `Gallery` beyond the first, or any single image appearing after the post's opening paragraphs.

**Correction from empirical verification (task 5.1, 2026-08-07)**: this was originally framed as "left as an explicit prop rather than auto-detected" — but that assumed the single-image and `Gallery`-child wiring would go through per-image React wrapper components with props, which task 3.1's revision (above) replaced with a client-side DOM-enhancement mechanism (`PostImageLightbox`/`Gallery` scanning already-rendered `<img>` elements). There is no per-image component instance left to attach a `priority` prop to, and plain markdown `![]()` syntax has no attribute syntax to set `fetchpriority`/`loading` per image either (confirmed: no attribute-syntax remark plugin, e.g. `remark-attr`, is installed in this repo). So "author explicitly marks an image as the LCP candidate" is **not achievable** within this change's current architecture without adding a new markdown-attribute-syntax mechanism — real new scope (a dependency + `astro.config.mjs` change), not a small addition, and deliberately not added speculatively since zero posts today actually open with a lead image (the epic's own audit: image embedding is greenfield). Tracked as an Open Question below rather than solved here.

**What's already true without any new code, verified via the scratch post**: `astro:assets`' `<Image>`/`getImage()` default every image to `loading="lazy"` regardless of position (confirmed: all 4 test images — the standalone one and all 3 `Gallery` children — render with `loading="lazy"` with no configuration from this change), and nothing anywhere sets `fetchpriority`, so the two hard constraints from this task's validation criteria ("no image has both `fetchpriority=high` and `loading=lazy`", "at most one image per page uses `fetchpriority=high`") are trivially satisfied today. The gap is the opposite direction from what the validation criteria checks for: there's currently no way to *turn off* `loading="lazy"` for a genuine future LCP-candidate image (e.g. a post that opens with a large photo) — that image would load slower than ideal, a real but currently-hypothetical performance cost given no post exercises this yet.

## Risks / Trade-offs

- **[Risk]** No image ever ships in this repo without being run through this design's tooling by hand — there's no lint/CI check enforcing that a post's images stay colocated with correct relative paths, so a broken image reference could ship silently (Astro's build would fail on a genuinely missing file, but a wrong-but-existing path, e.g. pointing at another post's image, wouldn't be caught). → **Mitigation**: `bun run build` (a required CI command) resolves all `astro:assets` imports at build time, so a missing file is a hard build failure, not a silent runtime 404 — this covers the main failure mode. Cross-post path confusion is a human-error risk accepted as proportionate to a personal blog's scale (verified: 10 posts today), not worth an additional custom lint rule.
- **[Risk, now resolved — task 5.2, 2026-08-07]** The lightbox might show a visibly lower-resolution image than a reader would expect at full-viewport size, if it relied on the grid thumbnail's own negotiated `srcset` candidate. **This risk doesn't materialize**, for a reason simpler than the mitigation originally anticipated: `LightboxImage.src` (built by `PostImageLightbox`/`Gallery` from the DOM as `img.src`) reads the `<img>` element's *`src` attribute*, not `img.currentSrc` (the browser's actual negotiated pick from `srcset`) — and `astro:assets`' `constrained` layout sets that `src` attribute to the *target* resolution derived from the source file's natural dimensions (confirmed: no explicit `width` is ever passed by the automatic rewrite, so `getImage()` defaults to the source's full natural size as the target). `Lightbox` never inherits the grid tile's smaller negotiated candidate at all, because it isn't reusing `srcset` negotiation — it's reading the one `src` value that already points at the image's full available resolution, independent of how small the grid CSS displayed it. Verified via Playwright against the scratch post: the standalone 2400×1600 source and each 800×600 `Gallery` source both open in `Lightbox` at their full natural pixel dimensions (`naturalWidth` matches exactly), regardless of the ~215px CSS grid tile they were clicked from. No `sizes`-attribute tuning needed; task 5.2 is otherwise a no-op given this.
- **[Risk]** `@headlessui/react`'s `Dialog`, like any React-portal-based modal, needs to be mounted client-side — if `client:visible` hydration is delayed (e.g. a reader deep-links directly to an anchor far down a long post, landing scrolled past the image before hydration completes), an early activation attempt on an image before hydration finishes does nothing. → **Mitigation**: same accepted degradation as `abf-k7d.1`'s `TableOfContents.tsx` used for its own `client:visible` scroll-spy — the image itself renders and is viewable inline immediately (not broken, just not click-to-enlarge yet), and `client:visible`'s own `IntersectionObserver` fires as soon as any part of the image scrolls into view, which for an inline content image is essentially immediate once visible at all.
- **[Risk]** This change touches `src/lib/mdx-components.tsx`, a shared-spine file the epic's own sequencing convention (see Context) flags as needing a collision check against sibling in-flight epics — `abf-k7d.3` is still in-progress as of this session. → **Mitigation**: `tasks.md` sequences the spine edit (registering `Gallery`) as its own late task, and this design explicitly calls out not starting it until `abf-k7d.3` lands or a fresh collision check clears it — component code (`Gallery.tsx`, `Lightbox.tsx`) that doesn't touch the spine can be built and tested in isolation first.

## Adversarial review and mitigations

This section reflects both this document's own review and a subsequent **independent** review (a fresh-context subagent, 2026-08-07, deliberately not shown this section's earlier draft) that verified claims against the actual repo and found real problems — those are folded in above as design revisions (Gallery's children-based shape, the keyboard-operable click target, the resolution risk, the deprecation-warning caveat, the spine-sequencing risk) rather than left as unresolved objections here, since they changed the design rather than just being noted and accepted. What remains below are objections considered and consciously accepted, not fixed:

- **Objection: "The epic's goal says galleries should work 'without requiring hand-authored JSX per post' — but this design's `Gallery` decision is exactly hand-authored JSX per post. That's not meeting the stated goal."** → Mitigation: the epic's goal text, read in full, is "without requiring hand-authored JSX per post" *in the context of* the epic's broader framing that some widgets (per `abf-k7d.2`, EChart/PigeonMap/DataTable) are already accepted as legitimately hand-authored JSX because their input is structured data, not prose. `Gallery`'s *grouping* (which images, in what order) is exactly this category. Individual images inside it, however, use plain markdown syntax (not a structured prop needing hand-typed paths) — the JSX surface is a single wrapping tag per gallery, not per image, and the single-image case (the "at minimum" scenario the epic calls out explicitly) requires zero JSX at all.
- **Objection: "Confirming the `@astrojs/mdx` automatic image rewrite by reading its source is not the same as confirming it actually works end-to-end in this repo's build — has anyone actually run `bun start` with a real image in a real post yet?"** → Mitigation: correct, this is source-code-level confirmation, not empirical confirmation. This design explicitly does not claim empirical verification — the Migration Plan's first step is exactly this: add a real image to a scratch/draft post and confirm via `bun start` before writing any new component code.
- **Objection: "This design doesn't address dark mode for the lightbox backdrop/controls, despite the repo clearly caring about light/dark parity."** → Mitigation: `@headlessui/react`'s `Dialog`/`DialogBackdrop` are unstyled by default — this repo's existing convention (confirmed via `button.tsx`/`callout.tsx` in `src/components/ui/`) is to style headless-ui primitives with `tailwind-variants` (`tv()`) against the existing `@theme` design tokens, which already have dark-mode-aware values. No new dark-mode-specific work is anticipated beyond applying the same `tv()`-plus-existing-tokens pattern already used elsewhere.
- **Objection: "Was `remark-gfm`'s image handling (already active repo-wide since `abf-k7d.1` landed) considered? GFM doesn't add new image syntax, but could it interact with the `astro:assets` rewrite in some unexpected way?"** → Mitigation: `remark-gfm` (confirmed via `abf-k7d.1`'s design.md, already merged) adds tables/strikethrough/task-lists/autolinks/footnotes — none touch markdown's standard image syntax (`![]()`), which is core CommonMark, unaffected by GFM extensions. No interaction expected; not verified empirically beyond this reasoning since there's no plausible mechanism for one, but noted here for the record rather than silently assumed.
- **Objection: "No automated test coverage is planned for `Gallery`/`Lightbox` at all — for interactive, accessibility-sensitive components, that seems like a real gap, not just deferred scope."** → Mitigation: accepted as a real gap, not dismissed — see Non-Goals and Open Questions. `vitest.config.ts`'s `test.include` (`['src/**/*.test.ts']`, confirmed by reading the file) would silently skip a `.test.tsx` file, so adding real component tests here would first require fixing that glob (and picking a testing-library approach) as its own piece of work, not something to bundle unreviewed into this change's task list. Manual verification (per `tasks.md`'s Validation steps: keyboard-only pass, screen-reader-adjacent checks like focus-return, light/dark mode) is the accepted bar for this change; automated coverage is flagged as follow-up work.

## Migration Plan

No data migration; no existing content is affected (zero posts currently use images). Deploy as a normal PR:
1. Add a real (or realistic placeholder) image to a scratch/draft post folder, reference it with plain `![]()` markdown syntax, run `bun start`, and confirm the automatic `astro:assets` rewrite produces optimized output (inspect rendered `<img>`/`srcset` in devtools, including actual candidate widths, relevant to the resolution Risk above).
2. Build `Lightbox.tsx` (the shared modal, `@headlessui/react`-based) and the focusable `<button>` click-target wrapper, wire it to the single embedded image first (the simpler case) — confirm keyboard-operable open, Esc/backdrop close, focus-return, and dark-mode styling.
3. Build `Gallery.tsx` as a children-based wrapper (plain markdown images nested inside `<Gallery>...</Gallery>`), confirm each child image still gets `astro:assets` optimization via the same automatic rewrite (no separate resolution logic needed in `Gallery.tsx` itself), and wire it to open `Lightbox` with next/previous navigation across its children.
4. Register `Gallery` in `src/lib/mdx-components.tsx` so it's usable directly in MDX body content without a per-post import — **held until `abf-k7d.3` lands or a spine-collision check clears it**, per the Context sequencing note.
5. Verify via a real scratch/draft post exercising both a standalone image and a `Gallery`, in both light and dark mode, keyboard-only and mouse.
6. No rollback complexity beyond a normal revert — nothing stateful or irreversible; no posts today depend on this feature existing.
