# Replacing the staged/in-progress blog workflow

Research only.
No repo files were changed to produce this document.

## Scope and method

Read `src/content/blog/AGENTS.md`, `src/content.config.ts`, and several real folders (`2026-01-13_the-hidden-costs-of-flexible-time-off`, `2026-03-14_bot-and-fraud-tsunami-in-tech`) to see the current mechanics and actual content quality.
Read `storagemaxxing/openspec/config.yaml` and `storagemaxxing/openspec/schemas/beads-driven/schema.yaml` as the concrete precedent for how this user wires beads and OpenSpec together elsewhere.
Confirmed `bd` (beads 1.1.0) is already initialized in this repo (`.beads/` exists, created the same day as this research).
Searched prior art on digital gardens, PARA, Zettelkasten, TIL repos, and SSG draft conventions.

## Diagnosis: hypotheses, not facts

The user said only "I hate the current format," not why.
Plausible pain points inferred from the mechanics, to validate before committing to a redesign:

- **No dashboard.** Across a dozen-plus folders, "what's active" requires manually scanning folder names and grepping `status:` fields. Nothing surfaces stalled vs. active ideas.
- **Two-phase file ceremony.** Creating `notebook.md`, then later creating a separate `index.mdx` and copying/re-deriving structure from the notebook, may feel like busywork for short posts.
- **Frontmatter status is a manually-flipped flag.** `status: concept|draft|review|published|locked` (see `src/content.config.ts:31`) is easy to forget to update, and is the only source of truth for both build visibility and planning state.
- **No lightweight capture.** A fleeting idea has no home smaller than "make a folder and a notebook file." Compare the existing `2026-03-14_bot-and-fraud-tsunami-in-tech` folder, which is a perfectly good notebook but required full folder ceremony for what might have started as a two-line thought.
- **Folder-per-idea may not scale as an index.** With growth, `ls src/content/blog/` becomes the de facto backlog view, which doesn't filter, sort, or show state at a glance.

## Prior art scanned

**Digital gardens / evergreen notes.** Maggie Appleton's garden tags every note with a growth stage — seedling (rough, early), budding (structured but unfinished), evergreen (mature, stands alone) — instead of a binary published/unpublished flag ([maggieappleton.com/evergreens](https://maggieappleton.com/evergreens)).
Andy Matuschak's working notes take the same idea further: notes are permanently "in progress," densely linked, and published continuously rather than gated behind a draft/publish switch ([notes.andymatuschak.org](https://notes.andymatuschak.org/), summarized via [matt.roam.garden/evergreen-notes](https://matt.roam.garden/evergreen-notes/)).
Both systems replace a binary gate with a maturity spectrum, and treat the note itself (not a separate tracking system) as the record of where an idea stands.

**PARA vs. Zettelkasten for blogging.** Consensus across sources is these solve different layers, not competing systems: Zettelkasten atomizes and links ideas; PARA (Projects/Areas/Resources/Archive) organizes files/folders by actionability ([zainrizvi.io/blog/para-vs-zettelkasten-the-false-binary](https://www.zainrizvi.io/blog/para-vs-zettelkasten-the-false-binary/)).
The Zettelkasten method site describes a direct zettel-to-blog pipeline: tag a note `#publish` when it's a post candidate, edit for public consumption, publish, then feed reader feedback back into the original note ([zettelkasten.de/posts/blogging-zettelkasten-fast-feedback](https://zettelkasten.de/posts/blogging-zettelkasten-fast-feedback/)). This is close to the existing notebook→mdx idea, but the tag (state) lives with the note, not in a separate two-file split.

**TIL repos.** Simon Willison's `til` repo is one markdown file per topic in a topic-named folder, no draft/publish gate at all — a file that exists, exists (published on write) ([github.com/simonw/til](https://github.com/simonw/til), [til.simonwillison.net](https://til.simonwillison.net/)). The index page is generated by a GitHub Action, not hand-maintained ([simonwillison.net/2020/Apr/20/self-rewriting-readme](https://simonwillison.net/2020/Apr/20/self-rewriting-readme/)). This pattern only works because TILs skip the "in-progress" state entirely — there's no staging problem to solve because nothing is staged.

**SSG draft conventions.** Current Astro best practice is a typed `draft`/`status` field in the content collection schema (exactly what this repo already does), filtered out at build time; the ecosystem debate is whether to keep it a boolean or an enum, not whether to move away from frontmatter-as-source-of-truth ([johndalesandro.com](https://johndalesandro.com/blog/astro-manage-draft-and-published-post-statuses-by-adding-a-content-collection-schema-property/)). Hugo and Eleventy handle it similarly, with less schema enforcement. None of the SSGs have an opinion on cross-post backlog visibility — that's consistently left to external tooling.

**Git-native, CLI-first trackers.** A growing class of tools (Backlog.md, git-issues, kanban-md) store Kanban-style task state as markdown+frontmatter files in-repo, explicitly for solo devs and AI agents, with a CLI to list/filter/board them ([github.com/MrLesk/Backlog.md](https://github.com/MrLesk/Backlog.md), [steviee.github.io/git-issues](https://steviee.github.io/git-issues/)). This is functionally what `bd` already is for this repo — the user doesn't need a new tool here, just to point the existing one at blog content.

**Folders vs. tags.** Broad consensus: folders give "a sense of place" and answer "what's active" at a glance but only one location per item; tags give cross-cutting discovery but degrade into a "junk drawer" without an active/archive backbone ([evernote.com/learn/folders-vs-tags](https://evernote.com/learn/folders-vs-tags-which-is-better-for-note-taking), [blog.shuvangkardas.com/obsidian-note-organization](https://blog.shuvangkardas.com/obsidian-note-organization/)). The strongest pattern is hybrid: minimal folder structure for lifecycle/location, tags for theme and cross-reference.

## Candidate approaches

### A. Flat, growth-stage digital garden (Appleton/Matuschak-style)

Drop the folder-per-post convention.
All notes live flat (or by year) as `.md`/`.mdx` files; a `stage: seedling | budding | evergreen` frontmatter field replaces `status`; everything is visible always (dev and prod), just labeled by maturity.

- **Better:** Kills the two-phase file ceremony outright — one file, evolving in place. Growth stage is a richer, more honest signal than a binary draft/publish gate; "seedling" openly invites half-formed public thinking, which many technical-writer gardens use well.
- **Worse:** This repo's prod/dev split and audience (a "personal blog," not an explicit garden) may not want seedlings live in prod — that's a philosophy change, not just a mechanics change, and the user didn't ask for that. Loses per-post co-located assets (`data.csv`, `map.ts`) that the current folder convention supports naturally in Astro's content collections. Doesn't solve the dashboard problem by itself — flat files still need something to list/filter them.

### B. Beads-as-pipeline, content only materializes late

Every idea starts as a `bd` issue (`bd q "post idea: ..."` for the two-second capture), not a file.
No `notebook.md`/folder is created until the idea has enough substance to research; the bead carries stage via labels (`blog`, `stage:seed`/`stage:researching`/`stage:drafting`), and `bd list -l blog` / `bd query` is the dashboard — solving the "no place to see what's in flight" problem directly with a tool already being adopted, not a new one.

- **Better:** Directly fixes the dashboard gap; capture-cost for a fleeting idea drops to one CLI command instead of "make a folder, make a file." Reuses tooling investment already underway (beads) instead of inventing bespoke content-status machinery. Bead dependencies/priority/defer let stalled ideas be queried explicitly (`bd query "status=open AND label=blog AND updated<-30d"`-style), which frontmatter can't do at all today.
- **Worse:** Splits state across two systems (bd for planning, frontmatter `status` for build visibility) unless kept in sync deliberately — same failure mode as today's "forget to flip status" problem, just relocated. Bead issues are optimized for engineering tasks (acceptance criteria, dependencies, close-with-validation); forcing prose-research and voice/narrative work through that shape is friction in the other direction. Doesn't remove the notebook→mdx split, only what precedes it.

### C. Hybrid — keep folder co-location, move planning state to beads, collapse the phase gate

Keep `YYYY-MM-DD_slug/` folders (needed for co-located assets and matches Astro's loader glob already in `src/content.config.ts`).
Replace the *notebook.md-then-index.mdx-as-separate-trigger* ceremony with: a `bd` issue is the capture step and the single source of planning/lifecycle state; the folder+notebook is created only once an idea is worth researching (unchanged from today); `index.mdx` frontmatter keeps a minimal `draft: boolean` purely as the Astro build-visibility switch (not a 5-value lifecycle enum); the bead, not the frontmatter, tracks concept → researching → drafting → review → published, and a bead label links back to the folder slug for traceability.

- **Better:** Solves the dashboard problem (bd is the backlog view) without inventing new tooling. Solves the capture-cost problem (`bd q` is cheaper than a folder). Removes the "forget to flip status" failure mode from the file people actually forget to touch, by making frontmatter's job trivial (one boolean, defaults sanely) while `bd` — which the user is already deliberately checking as part of infra work — owns the nuanced state. Preserves everything that already works: notebook-as-frozen-research-record, co-located assets, existing content collection loader/schema shape (small diff, not a rewrite).
- **Worse:** Two things to touch per post lifecycle event (bead + file), same as candidate B, though the split is cleaner (bd = planning, file = content/build). Requires a small amount of glue discipline (a bead label convention, e.g. `blog:<slug>`) that has no build-time enforcement — nothing stops it from drifting the way `status` drifts today, though the failure mode is now "stale bead," not "wrong prod visibility," which is lower stakes. Does not use OpenSpec at all for individual posts (see below) — if the user specifically wanted OpenSpec-for-posts, this recommendation pushes back on that.

## On OpenSpec specifically

The `storagemaxxing` `beads-driven` schema (`openspec/schemas/beads-driven/schema.yaml`) is built for engineering changes: proposal → specs → design → tasks → retrospective → reflection, each gated on the previous, with tasks hand-authored as checkboxes synced *from* bd state (never hand-flipped) and a strict apply protocol (claim → execute → close → push).
That machinery exists to keep multi-session/multi-agent engineering work auditable and to gate code review.
A blog post has no analogous "implementation correctness" gate, no dependent packages, and no code review step — applying the full proposal/design/tasks/retrospective chain per post would add more ceremony than the current notebook/mdx split, not less, which cuts directly against "I hate the current format."

Recommendation: don't use OpenSpec for individual posts.
Do use it once, at the meta level, to plan and execute *this workflow migration itself* (schema.ts changes, AGENTS.md rewrite, any migration script) — that is exactly the kind of infra change OpenSpec is already scoped for in this repo's adopted pattern.

## Recommendation

**Candidate C (hybrid): fold planning/lifecycle state into beads, keep the folder+notebook research shape, shrink frontmatter to a build-visibility boolean.**

This is the smallest change that plausibly fixes the hypothesized pain points (no dashboard, easy-to-forget status, no cheap capture) without discarding what already works (notebook-as-permanent-research-record, per-post asset co-location, existing Zod schema/loader).
It also directly reuses the tool the user is already deliberately adopting, rather than introducing a fourth system (frontmatter + folders + OpenSpec + something new).

### Sketch: capture

```
bd q "post idea: hidden costs of flexible time off" -l blog,stage:seed
# -> prints bd-xxxx, nothing else happens; no folder yet
```

### Sketch: promote to research (unchanged from today, plus a link back)

```
bun new-idea "Hidden costs of flexible time off"
# creates src/content/blog/2026-01-13_the-hidden-costs-of-flexible-time-off/notebook.md
bd update bd-xxxx --parent <blog-epic> -l blog,stage:researching --external-ref "content:2026-01-13_the-hidden-costs-of-flexible-time-off"
```

### Sketch: drafting trigger (replaces "user explicitly says start writing")

```
bd update bd-xxxx -l blog,stage:drafting
# creates index.mdx; frontmatter:
```

```yaml
---
title: "The hidden costs of flexible time off"
description: "..."
pubDate: 2026-01-13
draft: true   # was: status: concept|draft|review|published|locked
labels: ["finance"]
bead: bd-xxxx  # optional, only if you want a click-through from post to planning state
---
```

### Sketch: dashboard (the thing that doesn't exist today)

```
bd query "label=blog AND status=open" --sort updated
# or, per stage:
bd list -l blog,stage:drafting
```

### Sketch: publish

```
bd close bd-xxxx --reason "published"
# and flip draft: false in index.mdx frontmatter (the only frontmatter edit left)
```

### Schema diff implied (`src/content.config.ts`)

Replace:

```ts
status: z.enum(['concept', 'draft', 'review', 'published', 'locked']).default('published'),
```

with:

```ts
draft: z.boolean().default(false),
```

This matches the community-preferred Astro pattern cited above and removes the 5-state enum whose nuance now lives in `bd`, not in the file.

## Open questions for the user (don't guess past these)

- Is `notebook.md` genuinely fine as-is, or was some of the "hate" actually about the notebook/research phase too, not just the status-tracking phase?
- Should `stage:*` be a label convention on one epic-per-post bead, or should each lifecycle transition be its own child bead (closer to how `storagemaxxing` tasks work)? The sketch above assumes the former (simpler) but the user may want the audit trail of the latter.
- Is there an appetite for a `bun` script (à la `fix:tasks` in `storagemaxxing`) that renders the `bd query` dashboard into a checked-in `BACKLOG.md`, so the dashboard is visible without running `bd` — worth doing only if GitHub-browsing the backlog matters, otherwise `bd query` alone is enough for a single local writer.
