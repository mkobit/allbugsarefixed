## Context

The blog's staged/in-progress workflow today is `YYYY-MM-DD_slug/notebook.md` → `index.mdx`, gated by a 5-value `status` frontmatter enum (`concept|draft|review|published|locked`, `src/content.config.ts`).
Most folders under `src/content/blog/` today are notebook-only, pre-dating any bead tracking; as of this writing only 3 have an `index.mdx`:
- `2026-01-13_the-hidden-costs-of-flexible-time-off`: `status: "concept"`
- `2024-01-01_measuring-commute-cost` and `2024-05-20_tech-demo`: **no `status` field at all** — implicitly `published` today via the schema's `.default('published')`
- Every other folder has `notebook.md` only, no `index.mdx`, and no corresponding bead — exactly the "no dashboard of what's in flight" problem this change exists to fix. (Deliberately not pinning a count here — it changes every time someone starts a new idea. The migration step below enumerates them fresh at execution time.)

This matters directly for the migration plan below: the two status-less posts are live in prod today, and any change to the visibility field's default must not silently unpublish them.

Two problems motivate this change (see `proposal.md`):
1. No dashboard of what's in flight, and a manually-flipped `status` field that's easy to forget.
2. `notebook.md` — meant to be a fact/link/quote scratchpad — keeps getting turned into agent-written, blog-voiced prose (and stray code) by delegated agents (Jules and others), bleeding into the eventual post's voice.

`bd` (beads) is already adopted in this repo, including a molecule/formula system (`bd mol pour`) used elsewhere (`openspec-sync` formula) to spawn a DAG of child issues from a template. Sibling repos (`canopy`, `storagemaxxing`) have prior art for multi-step formulas (e.g. `storagemaxxing/.beads/formulas/feature-probe.formula.toml`): each `[[steps]]` entry becomes a child issue under a root epic, and the repo's own convention treats step order as sequential unless a step explicitly signals otherwise (e.g. `human-review`'s description says to mark itself `blocked`).

## Goals / Non-Goals

**Goals:**
- Move lifecycle/planning state out of frontmatter and into beads, with a dashboard (`bd list -l blog`) that already exists as a beads capability.
- Give each idea's lifecycle transitions their own audit trail (timestamps, notes) without hand-building a bespoke child-bead scheme — reuse the molecule/formula mechanism already used for `openspec-sync`.
- Structurally reduce the chance that research capture turns into agent-written prose or stray code, since documentation alone (`AGENTS.md`) has not prevented this in practice.
- Keep frontmatter to the one thing Astro actually needs at build time: is this post visible or not.

**Non-Goals:**
- Not changing the `YYYY-MM-DD_slug/` folder shape, `notebook.md` → `index.mdx` two-file convention, or the Astro content-collection loader.
- Not building new tooling — `bd list`/`bd mol progress` is the dashboard.
- Not addressing hosting (GitHub Pages vs CloudFront, `abf-zdv.3`) or live/prod testing (`abf-zdv.2`) — separate epics.
- Not migrating historical git history of `notebook.md` content; this is a forward-looking process change.

## Decisions

**1. Lifecycle tracking via a `blog-lifecycle` beads formula, poured once per idea, rather than a single label flip.**
`bd mol pour blog-lifecycle --var slug=<kebab-slug> --var title="..."` creates a root epic plus five child issues (`seed`, `researching`, `drafting`, `review`, `published`), explicitly chained via each step's `depends_on` field (an array of sibling step ids) so closing one unblocks the next. Advancing a stage = closing the current stage's bead, which unblocks the next.
*Why `depends_on` and not declaration order:* this repo's own sibling formulas (`openspec-sync.formula.toml`, and `storagemaxxing/.beads/formulas/feature-probe.formula.toml` used as prior art) do **not** chain their `[[steps]]` — an adversarial review of this design confirmed, by pouring `feature-probe` for real and inspecting with `bd mol show --parallel`, that all steps land in one unblocked parallel group with zero dependencies between them; the apparent sequencing in `feature-probe` is enforced only by step-description text telling the agent what order to work in, not by real blocking.
*Why `depends_on` and not `after_step`:* the `bd` binary's TOML tags advertise both `after_step` (singular string) and `depends_on` (list) fields on a step — that was the adversarial review's binary-string evidence for "real chaining exists." Implementing `blog-lifecycle.formula.toml`, both were tested empirically with a throwaway scratch formula and a real pour: `after_step = "a"` produced **zero blocking** (the step showed as immediately ready, no dependency edge created), while `depends_on = ["a"]` produced a correct, verified dependency edge (`bd mol show --parallel` showed it blocked, and closing `a` unblocked it). `after_step` is not used anywhere in this formula. This is the same lesson as the adversarial review's finding 1, one layer deeper: binary string presence of a field doesn't mean it's wired up to do what its name suggests — verify with a real pour, every time.
*Why over a single-bead label flip:* the original proposal draft considered a single bead with a `stage:*` label that gets edited in place. That's simpler but loses per-transition timestamps and requires remembering to flip a label (the same failure mode as the `status` field it replaces). A molecule with real dependency chaining gives that audit trail for free since every `bd` issue already has created/closed timestamps, and `bd ready`/`bd mol progress` becomes the "what's next" view instead of a manually-maintained label.
*Why over a child-bead-per-transition hand-rolled scheme:* that's what a molecule formula *is* — building it as a reusable formula means every future post idea gets the same structure with one command, instead of manually creating five linked issues per idea.
*Alternative considered:* keep `bd q "post idea: ..."` for zero-ceremony capture, and only pour the fuller molecule once an idea graduates past `seed`. Rejected for now — pouring the whole molecule at capture time is still one command, and having the `seed` bead already exist as stage 1 of the same molecule avoids a manual "convert this quick-capture bead into a molecule" step later. If in practice `seed`-stage ideas pile up unused, this is cheap to revisit (see Open Questions).

**2. Formula step descriptions carry the notebook/prose guardrail directly, not just `AGENTS.md`.**
The `researching` step's description in `blog-lifecycle.formula.toml` states explicitly: `notebook.md` is fact/link/quote/rough-note capture only; no publish-voice prose; code or data goes in auxiliary files (`data.csv`, `map.ts`), not inline.
*Why:* `AGENTS.md`'s existing persona section already says "Do Not: Write the prose... Do not try to mimic the user's voice," and this has not been followed in practice by delegated agents. Putting the constraint on the bead itself — what an agent actually reads when it claims `stage:researching` — is a second, more proximate surface for the same rule, on the theory that a static doc gets skimmed once while a live task's description is read at point of work. `AGENTS.md` is still rewritten for the human-facing/canonical version of the rule; the formula text is a duplicate, not a replacement.

**3. `notebook.md`'s template is reworked to structurally discourage prose.**
Current template (`scripts/new-idea.ts`): `# Title` / `## Idea` / `## References` — an open `## Idea` heading invites free-form paragraphs. New template uses headers that read as capture buckets, not essay sections (exact headers are an implementation detail for `tasks.md`, but the direction is: separate raw links/quotes from the human's own rough thoughts from agent-research findings, with no heading that reads as "write the post here").
*Why structural over documentation-only:* same reasoning as (2) — a template shape nudges behavior at the point of writing, which has proven more reliable than a policy statement elsewhere in this same file.

**4. Frontmatter collapses to `visibility: 'hidden' | 'unlisted' | 'visible'`, not a boolean.**
Replaces the 5-value `status` enum. `locked` currently has zero real usage, so no behavior is lost in the collapse. The schema field itself has **no default** — every `index.mdx` that exists or is created must set `visibility` explicitly. This is a deliberate change from the current schema's `.default('published')`: that default is what makes this migration dangerous (see below), and a build-visibility field should never silently decide a post's visibility via an unstated default. `astro check`/`bun typecheck` (already a required CI gate per `AGENTS.md`) enforces this at build time once the field is required.
*Why a 3-value enum and not `draft: boolean`:* an earlier draft of this decision used a boolean. Revised after direct pushback: a plain on/off flag is the right shape only if build visibility is genuinely binary, and it isn't — the current code already has two independently-checked visibility concerns (does this post get a page built at all, and does it show up in listings/search), and collapsing both into one boolean would have papered over that rather than fixing it. `unlisted` is a real, useful third state this repo doesn't have today: a page is built and reachable by direct URL, but excluded from listings/search — useful for sharing a link before full announcement. This isn't "bring back the 5-value enum"; it's a deliberately smaller, purpose-built set scoped to build visibility only (lifecycle stays entirely in beads, per Decision 1).
*Consumer sites (repo-wide grep, no RSS/feed file exists), mapped to the new enum:*
- `src/pages/blog/[...slug].astro` prod static-path gate: build a page for anything **not** `hidden` (`visibility !== 'hidden'`) — both `unlisted` and `visible` get real pages. The per-status badge (which today renders whatever the raw status string is) shows the `visibility` value whenever it isn't `'visible'`, since in dev mode all three states render and a hidden/unlisted post still benefits from an at-a-glance indicator.
- `src/layouts/Layout.astro` search index and `src/pages/blog/index.astro`/`src/pages/index.astro` listing filters: only `visibility === 'visible'` — both `hidden` and `unlisted` are excluded from listings/search, which is exactly what makes `unlisted` meaningfully different from `visible`.
*Side effect:* today's `Layout.astro` search index only includes `status === 'published'`, while `[...slug].astro`'s prod static-path gate also allows `'locked'` — an existing inconsistency (a `locked` post would build a page but not appear in search, and a `review`-status post would appear in listings per `blog/index.astro`'s filter but 404 when clicked, since `[...slug].astro` never built it). The 3-value enum fixes this by construction: exactly one field, two consistent checks (`!== 'hidden'` for page-exists, `=== 'visible'` for listed), no more independently-drifting conditions.
*Correction from adversarial review:* an earlier draft of this decision defaulted the visibility field to always-published and claimed "only one post exists," which is wrong (see Context) — two posts (`2024-01-01_measuring-commute-cost`, `2024-05-20_tech-demo`) have no `status` field and are live in prod today via the `'published'` default. A silent default would have silently unpublished them; a required field with no default, paired with an explicit migration step per existing post, avoids that.

**5. `notebook.md` and `index.mdx` merge into a single `index.mdx` per post; a reserved `## Scratch` heading delimits the research section, stripped from every render by a new remark plugin.**
Per `abf-zdv.4.17`'s decision (adopt single-file-with-purge over the two-file split this change originally shipped — see that bead's `--design` field for the full comparison), `YYYY-MM-DD_slug/notebook.md` and `index.mdx` become one file: `YYYY-MM-DD_slug/index.mdx`. Research capture (facts, links, quotes, rough notes — same content shape as today's `notebook.md` template) moves into a `## Scratch` section within that file instead of a separate file. `index.mdx` is now created at the `stage:researching` transition (moved earlier than today's `stage:drafting` trigger, since there's no `notebook.md` left to create instead), with `visibility: "hidden"` set from creation.
A new remark plugin, `remarkStripScratch` (`src/lib/remark/remark-strip-scratch.ts`, `unist-util-visit` AST-transform shape modeled on `remarkCallout`/`remarkMermaidToComponent`, registered **first** in both `astro.config.mjs`'s `mdx({ remarkPlugins })` and `markdown.remarkPlugins` lists — ahead of `remarkReadingTime` — per this repo's existing dual-registration pattern), finds the section whose boundaries are computed by a shared helper (see Decision 6) and removes it from the mdast tree before HTML output — unconditionally, regardless of `visibility` or lifecycle stage, in both `astro dev` and prod builds.
*Why unconditional, not gated on stage/visibility:* `src/pages/blog/[...slug].astro`'s `getStaticPaths` renders every entry in dev regardless of `visibility` (the `isProd` check only filters which paths get statically built in prod — dev has no such filter, confirmed by reading the file directly). A strip gated on lifecycle stage or `visibility` would leave the scratch section fully rendered in dev preview for the entire research/drafting/review window, which is strictly worse than today, where `notebook.md` never renders in any environment (excluded at the content-collection loader level via `!**/notebook.md` in `src/content.config.ts`). Stripping unconditionally in the remark pipeline restores an equivalent structural guarantee — nothing under `## Scratch` reaches HTML output, in any environment, at any stage — which is what closes the gap the `abf-zdv.4.17` adversarial review flagged ("the only thing preventing a scratch leak becomes a purge step running correctly on every publish"): the render-time strip, not the purge script, is what actually prevents a leak; the purge script (Decision 6) is a file-hygiene operation, not the safety mechanism.
*Why a plain Markdown heading and not an HTML or JSX comment:* the `abf-zdv.4.17` review specifically flagged both as unreliable in MDX (HTML `<!-- -->` comments aren't guaranteed stable inside an MDX/JSX-aware parser; `{/* */}` breaks on a literal `*/` inside freeform notes). A depth-2 Markdown heading is unambiguous standard Markdown, needs no escaping, and is exactly the node type (`heading`) `remarkCallout` already visits successfully today — no new parsing risk class introduced.
*Why the document body and not frontmatter:* keeping scratch content in the document body means the free-text capture shape that already works (headings, bullets, quotes, tables — the same shape as today's `notebook.md` template) carries over unchanged into the merged file; only "where research starts" is new, not "how research is written." `## Scratch` becomes a reserved heading — documented in `AGENTS.md` as a hard constraint (a post's real content must not use that literal heading at depth 2), the same class of rule as today's "no blog-voice prose in notebook.md."
*Correction from adversarial review:* the original draft matched the heading the way `remarkCallout` matches its trigger text — inspecting only `node.children[0]` for a `text` node. That's insufficient here: a heading written as `## **Scratch**` has a `strong` first child, not `text`, so the shallow check silently fails to match and the section renders live, unstripped, with no warning. **Fixed:** heading-text matching uses `mdast-util-to-string(headingNode).trim() === 'Scratch'` (new dependency — flattens all descendant text regardless of inline formatting), not a first-child shallow check. This is a correctness fix, not a style choice: it changes whether a legitimately-formatted `## Scratch` heading is recognized at all.
*Correction from adversarial review:* plugin order was originally unspecified. `remarkReadingTime` runs early in both existing `astro.config.mjs` lists; if `remarkStripScratch` ran after it, reading time would count scratch-section words for every WIP post during dev preview (deterministic, not rare, verified by reading current plugin order). **Fixed:** first sentence above now specifies `remarkStripScratch` registers first in both lists. Migration Plan step 4 (below) must also verify the reading-time badge, not just HTML content.
*Residual risk, not fully closed by this decision:* the "unconditional strip closes the render-safety gap" claim holds only for well-formed MDX. `getStaticPaths` applies no `visibility` filter in dev, so a scratch-section MDX syntax error (stray `<`, unbalanced `{`) can break MDX compilation before the strip transform ever runs, and Astro's dev error overlay can show a raw source frame. This is local-dev-only, not a public/prod leak, and is addressed by the existing "no inline code" guardrail (Decision 2/3) rather than by this mechanism — noted here explicitly rather than claiming the gap is fully closed (see Risks).

**6. A shared, AST-derived boundary function locates the scratch section; the remark plugin strips it from the render tree, and a separate purge script slices the *raw source text* at the same boundary offsets — both AST-correct, neither reformats the surviving file.**
`src/lib/remark/scratch-section.ts` exports one pure function, `findScratchSection(tree): { start: number; end: number } | null`, operating on a parsed mdast tree: it locates the `heading` node at depth 2 whose flattened text (via `mdast-util-to-string`) is exactly `Scratch`, and returns the byte offsets (`node.position.start.offset` through the position immediately before the next depth-≤2 heading, or EOF) spanning that heading and everything until the next same-or-shallower heading. Both consumers call this one function:
- `remarkStripScratch` (Decision 5) calls it against the tree Astro's MDX pipeline has already parsed, then removes the matched node range from that tree before HTML output.
- `scripts/purge-scratch.ts` (`bun run purge-scratch <slug>`, following the `new-idea.ts`/`verify-blog-structure.ts` pattern of a standalone Bun script) independently parses the target `index.mdx` with `unified().use(remarkParse).use(remarkMdx)` (parse-only — **no `remark-stringify`**), calls `findScratchSection`, and slices the *original raw source string* to remove exactly the returned offset range, then writes the result back verbatim. Everything outside that range is untouched byte-for-byte, because the output is a string slice of the original source, not a re-serialized AST.
*Correction from adversarial review:* the original draft rejected any AST parsing for the purge script and instead line-matched for a literal `## Scratch` string in the raw text. That's a real bug, not a stylistic simplification: a fenced code block containing the literal text `## Scratch` (e.g. a ```` ```md ```` example inside the scratch section itself, or in this very design doc's own prose) is a single opaque `code` leaf node in mdast — the AST-based remark plugin correctly ignores it, but a naive line-scanner would match it and corrupt an unrelated section. **Fixed:** the purge script parses the file (read-only) to find correct AST boundaries, then slices raw text at those offsets — this keeps Decision 6's original goal (don't run the whole file through `remark-stringify`, which would reformat every line and defeat a surgical purge) while fixing the code-fence false-positive, and it eliminates the earlier "do the strip plugin and purge script even agree?" risk by construction: they now call the identical boundary function instead of two independently-implemented notions of "the scratch section." New dev dependencies: `remark-parse`, `remark-mdx` (parse-only, matching the syntax Astro's own MDX pipeline accepts), `mdast-util-to-string`.
*Why `review`→`published`, not `drafting`→`review`:* mirrors the existing `AGENTS.md` "Publishing" step, which is already the exact transition where `visibility` flips to `"visible"` — adding "purge scratch" to that same step is a minimal process change (one more action at an existing trigger) rather than a new trigger. Keeping scratch material through `review` also means a final read-through/fact-check pass (the stated purpose of the `review` stage) still has its sourcing material available; purging before review would remove it exactly when it's most likely to be needed.
*Why manual, not automatic:* there's no CI hook or git hook tied to bd state transitions in this repo today (`bd close` doesn't trigger a script), and building one is out of scope for this bead — `abf-zdv.4.18`'s scope is the file-shape mechanism, not new automation infrastructure. The purge step is documented in `AGENTS.md`'s Publishing section as an explicit action, the same ergonomic level as today's manual "flip `visibility`, close the bead" steps.

**7. Purged content is deleted outright; git history is the archive, not a second file or location.**
`scripts/purge-scratch.ts` deletes the scratch section's lines from the working file; it is not moved to another file, branch, or directory. Recovery, if ever needed, is `git log -p -- <path>` / `git show <commit>:<path>` against the pre-purge commit.
*Why, despite the `abf-zdv.4.17` review's caution that "purged material should be archived, not deleted... writers want it back":* archiving to a second file or location was explicitly identified in that same review as the risk of "collapsing the mechanism back into needing a second file/location anyway" — which is the exact two-file overhead this change is trying to remove. Git already retains full history of every commit to `index.mdx`, including the pre-purge state with the scratch section intact, for as long as the repository exists — for a single-author, low-volume blog (this repo, not the multi-writer CMS context the reviewer's general research was likely generalizing from), `git log`/`git show` is a low-friction enough recovery path that a dedicated archive mechanism isn't justified. This is a real trade-off, not a dismissal of the review's point — flagged explicitly here and in Risks below rather than decided silently.

## Risks / Trade-offs

- **[Risk] Pouring a 5-stage molecule for every fleeting idea is heavier than a bare `bd create`.** → **Mitigation:** it's still one command; `bd mol burn`/closing the root epic handles abandoned ideas the same as closing any bead would.
- **[Risk] Formula step descriptions drift out of sync with `AGENTS.md` since the guardrail text now lives in two places.** → **Mitigation:** treat `AGENTS.md` as canonical and the formula text as a short pointer/summary rather than a full restatement, reviewed together whenever either changes (call out in the PR description, not enforced by tooling — acceptable given this is a two-person-scale repo).
- **[Risk] A template shape change doesn't actually stop an agent that's determined to write prose into `notebook.md`; it only nudges.** → **Mitigation:** this was already true of the current `AGENTS.md`-only approach and is not made worse; genuinely preventing it would require a build-time or CI check (e.g. flagging long paragraph runs in `notebook.md`), which is out of scope for this change and can be filed as a follow-up if the structural nudge proves insufficient in practice.
- **[Risk] Nothing prevents or detects pouring `blog-lifecycle` twice for the same slug**, and an abandoned `stage:seed` bead looks identical to "not started yet." → **Mitigation:** the capture instructions (`AGENTS.md` rewrite, task in `tasks.md`) must include a pre-pour check (`bd search <slug>` or `bd query "label=blog AND external_ref~<slug>"`) before running `bd mol pour`.
- **[Risk] Several existing folders have `notebook.md` only, no `index.mdx`, and no bead** — silently excluded from the new dashboard, leaving the exact "no visibility into what's in flight" problem unsolved for pre-existing ideas. → **Mitigation:** added as an explicit Migration Plan step (backfill a `blog-lifecycle` pour at `stage:researching` for each) rather than left implicit.
- **[Risk, verified during adversarial review] `.formula.toml` `[[steps]]` are NOT chained by declaration order** — confirmed by pouring the prior-art `feature-probe` formula for real and inspecting with `bd mol show --parallel`: all steps land in one unblocked group. → **Mitigation:** addressed directly in Decision 1 above (`blog-lifecycle.formula.toml` sets `depends_on` explicitly on every step after `seed`; `after_step` was tried too and confirmed to do nothing); `--dry-run --json` does not surface dependency info, so verification must be pour → `bd mol show --parallel` → delete the test pour, not a dry-run.
- **[Risk] `## Scratch` collides with a legitimate depth-2 heading a post's real content wants to use.** → **Mitigation:** reserved-heading constraint documented in `AGENTS.md` (Decision 5); `findScratchSection` (Decision 6) should also throw at build time if it finds more than one matching heading in a single file (matching `remarkCallout`'s existing pattern of throwing on an invalid callout type), surfacing misuse early instead of silently stripping the wrong content.
- **[Risk, verified during adversarial review, fixed] The render-time strip (Decision 5) and the purge script (Decision 6) originally used two independently-implemented notions of "the scratch section"** — a shallow first-child text check in the remark plugin, a raw line-scan in the purge script — which disagree in real cases: a heading with inline formatting (`## **Scratch**`) could evade the shallow check, and a fenced code block containing the literal text `## Scratch` (plausible in this very design doc, or in a scratch-section example) would be wrongly matched by a line-scan while correctly ignored by the AST. → **Fixed, not just mitigated:** Decision 6 now defines one shared `findScratchSection` function, called by both the remark plugin and the purge script, so there are no longer two definitions to disagree.
- **[Risk] Forgetting to run `purge-scratch` at publish leaves scratch content in the shipped source file** (it still won't render, per Decision 5's unconditional strip, but it ships in the git-tracked file and in any raw-source distribution). → **Mitigation:** documented as an explicit `AGENTS.md` Publishing step (Decision 6); since Decision 5 already prevents any render-time leak, a missed purge is a hygiene miss, not a content leak — lower severity than the two-file design's `notebook.md`-never-deleted status quo, which already ships alongside every published post today.
- **[Risk] Deleting rather than archiving purged content (Decision 7) may be regretted later if research material would genuinely help a future revision of a published post.** → **Mitigation:** explicitly accepted trade-off, not an oversight — git history remains the recovery path; revisit only if this proves painful in practice (same "revisit after real usage" posture as this file's original Open Questions).
- **[Risk, verified during adversarial review] A scratch-section MDX syntax error can break compilation before `remarkStripScratch` ever runs, surfacing raw source in Astro's dev error overlay.** `getStaticPaths` applies no `visibility` filter in dev, so this isn't limited to already-public posts — but it is local-dev-only, not a public/prod leak. → **Mitigation:** covered by the existing "no inline code, no raw angle-bracket-bearing URLs" scratch-content guardrail (Decision 2/3), not by the strip mechanism itself; noted explicitly here rather than treating Decision 5's render-safety guarantee as absolute.

## Migration Plan

Order matters: frontmatter for every existing `index.mdx` is migrated **before** `content.config.ts` makes `visibility` a required field with no default, so the build is never in a state where an existing post is silently invalid or silently unpublished.

1. Write `.beads/formulas/blog-lifecycle.formula.toml` (5 steps chained via explicit `depends_on`, vars: `slug`, `title`). Verify chaining by pouring once, inspecting with `bd mol show --parallel`, then deleting the test pour — not `--dry-run` (see Risks).
2. Migrate all 3 existing `index.mdx` posts' frontmatter first, while `status` and `visibility` can briefly coexist:
   - `2026-01-13_the-hidden-costs-of-flexible-time-off`: `status: "concept"` → `visibility: "hidden"`
   - `2024-01-01_measuring-commute-cost`: (no field) → `visibility: "visible"`
   - `2024-05-20_tech-demo`: (no field) → `visibility: "visible"`
3. Update `src/content.config.ts`: `status` enum → `visibility: z.enum(['hidden', 'unlisted', 'visible'])` (no default — required field).
4. Update the 4 consumer call sites (`Layout.astro`, `[...slug].astro` ×2 usages, `blog/index.astro`, `pages/index.astro`) to read `visibility` instead of `status`, per the mapping in Decision 4; collapse the `[...slug].astro` status badge to show the `visibility` value whenever it isn't `'visible'`.
5. Backfill a `blog-lifecycle` pour (at `stage:researching`, since research has already started) for every existing notebook-only folder — enumerate fresh at execution time (`find src/content/blog -type d ! -name AGENTS.md` minus folders with an `index.mdx`), don't hardcode a count — so they're visible in the new dashboard instead of silently excluded.
6. Rework `scripts/new-idea.ts`'s notebook template.
7. Rewrite `src/content/blog/AGENTS.md`: lifecycle section describes the molecule-driven flow (including the pre-pour idempotency check); persona section gets explicit notebook-vs-prose DO/DON'T examples.
8. Run full CI gate locally (`bun lint`, `bun openspec:validate`, `bun typecheck`, `bun test`, `bun coverage`, `bun build`, `bun test:e2e`) before merge, per `AGENTS.md`.
9. Rollback: this is a frontmatter/tooling change affecting 3 real posts; rollback is a straightforward `git revert` of the migration commit(s), no data migration risk beyond those 3 posts' frontmatter and the backfilled molecules (which can simply be closed/burned).

## Migration Plan (single-file-per-post mechanism, `abf-zdv.4.18`)

Applies on top of the already-executed Migration Plan above; order matters here too — the render-time strip must exist and be verified before any real post's `notebook.md` content is merged into `index.mdx`, so a merge is never briefly unguarded.

1. Add dev dependencies: `remark-parse`, `remark-mdx`, `mdast-util-to-string` (parse-only tooling for `scripts/purge-scratch.ts`; no `remark-stringify` — see Decision 6).
2. Write `src/lib/remark/scratch-section.ts` (`findScratchSection(tree)`, shared by both consumers below — see Decision 6).
3. Write `src/lib/remark/remark-strip-scratch.ts`; register **first** in both `astro.config.mjs` remark-plugin lists (`mdx({ remarkPlugins })` and `markdown.remarkPlugins`), ahead of `remarkReadingTime`.
4. Verify the strip for real: create a scratch fixture post with a `## Scratch` section (including a fenced code block inside it containing the literal text `## Scratch`, and a `## **Scratch**`-formatted-heading fixture as a negative test), run `bun run start`, confirm the scratch section is absent from the rendered dev page AND that the reading-time badge excludes scratch-section word count (not just a unit test) — the same "verify empirically, don't trust binary-string/type-level evidence" lesson the `abf-zdv.4.17` and original `blog-workflow-overhaul` adversarial reviews both independently landed on.

## Adversarial review and mitigations

Performed by an independent agent with fresh context (no prior exposure to this design's authoring), per this repo's own `feature-probe` formula convention (`storagemaxxing/.beads/formulas/feature-probe.formula.toml`'s `hole-poking` step: adversarial review must not be the author re-reading their own work). Findings, each verified against real evidence rather than taken on faith:

1. **Core chaining mechanism didn't work as designed.** The design's original claim — that `[[steps]]` in a `.formula.toml` chain sequentially by declaration order, per sibling-repo convention — is false. Verified by pouring the prior-art `feature-probe` formula for real and inspecting with `bd mol show --parallel`: all 5 steps landed in one unblocked parallel group. The `bd` binary's TOML tags advertise both `after_step`/`depends_on` fields (confirmed via binary string inspection), but the formulas being copied as prior art use neither. **Fixed:** Decision 1 now specifies explicit chaining on every non-seed step — and a follow-up empirical test during implementation found `after_step` itself doesn't work either (only `depends_on` creates a real dependency edge), so binary-string evidence of a field's existence was still not sufficient; see Decision 1's second "why" note.
2. **The design's own verification plan for that risk didn't work either.** `--dry-run --json` output has no dependency info; only a real pour + `bd mol show --parallel` surfaces it. **Fixed:** Migration Plan step 1 and the corresponding Risk entry now specify pour → inspect → delete.
3. **"Exactly one post exists" was factually wrong.** At review time, 3 folders had `index.mdx`; 2 of those had no `status` field and relied on the schema's `.default('published')` — they're live in prod today. The original Decision 4 (a boolean defaulting to hidden) would have silently unpublished them. **Fixed:** Context section corrected; Decision 4 changed to a required field with no default; Migration Plan reordered so frontmatter migration happens before the schema change, with explicit `visibility` values for all 3 real posts.
4. **Several more folders are notebook-only with no bead at all** — the exact "no dashboard" problem this change targets, left unaddressed by the original migration plan. **Fixed:** added as Migration Plan step 5 (backfill a `stage:researching` pour for each, enumerated fresh at execution time rather than a hardcoded count — the original fix for this attempted to pin an exact number, which is exactly the kind of stale-the-moment-someone-adds-a-post rigidity this whole change is trying to get away from) and as a Risk entry.
5. **No idempotency guard on pouring the same slug twice.** Not something the reviewer could disprove or confirm empirically (it's a process gap, not a mechanism), but flagged as a real gap. **Fixed:** added as a Risk entry with a concrete mitigation (pre-pour `bd search`/`bd query` check, to be written into the `AGENTS.md` capture instructions).

Not flagged by the review, and therefore left as-is: the overall shape of Decisions 1–3 (molecule-per-idea over label-flip or hand-rolled child beads; guardrail text living in both the formula and `AGENTS.md`; notebook template rework) held up against the "is this justified vs. the rejected alternative" and "is this magical thinking" adversarial questions the reviewer was asked to specifically probe.

### Second pass: single-file-per-post mechanism (Decisions 5–7, `abf-zdv.4.18`)

Performed by a second independent agent with fresh context, same convention as above. Full rationale for each fix lives at the decision it changed, referenced below rather than restated:

1. Shallow heading-text matching (ported from `remarkCallout`) missed formatted headings like `## **Scratch**`. **Fixed** — Decision 5, first "Correction" note (`mdast-util-to-string` instead of a shallow check).
2. The AST-based strip and the original line-based purge script disagreed on fenced-code false positives (a literal `## Scratch` inside a code block). **Fixed** — Decision 6, shared `findScratchSection` function.

4. Plugin registration order was unspecified, risking reading-time miscounts on WIP posts. **Fixed** — Decision 5, `remarkStripScratch` now registers first in both lists.
5. Minor, no fix needed: a `stage:researching`-created `index.mdx` renders a mostly-blank dev page until drafting starts. Cosmetic, noted in the design.

Not re-verified, inconsequential either way: the `abf-zdv.4.17` review's claim that HTML/JSX comments are unreliable in MDX — Decision 5 sidesteps it by using a heading, not a comment.
